# Task Document Conventions

This file defines the standard rules and behaviors that apply to all task documents in this folder. Every task document must follow these conventions. When creating a new task document, read this file first.

---

## 1. Output File Frontmatter Standard

All output files generated by any agent task must include the following frontmatter fields. Both `date` and `time` are mandatory — a date alone is insufficient.

```yaml
---
date: "YYYY-MM-DD"
time: "HH:MM"
generated_by: "<Agent Name>"
inputs_used:
  - "<relative/path/to/input-file.md> (date: YYYY-MM-DD)"
---
```

**Rules:**
- `date` format: ISO 8601, e.g., `2026-05-16`
- `time` format: 24-hour local time at generation, e.g., `14:35`
- `inputs_used` lists every file the agent read to produce the output, with the date from that file's frontmatter
- If an input file has no `date` in its frontmatter, note `(date: unknown)` and flag it to the user

---

## 2. Pre-Flight Checks (Required Before Every Task Run)

Every task document must include a Pre-Flight Checks section. The agent must execute all checks before generating any output. Do not skip pre-flight checks.

### 2a. Prompt Confirmation

Before doing any work, present the standard prompt to the user and ask:

> "This is the standard prompt for this task: [prompt text]. Do you want to use it as-is, add to it, or replace it with a different prompt before I continue?"

Wait for the user's response. If the user confirms as-is, proceed. If the user modifies or replaces the prompt, record the change and proceed with the modified version. Never silently assume the prompt is approved.

### 2b. Input File Existence Check

Before reading any input file, verify it exists. If a required input file is missing, stop immediately and inform the user:

> "[filename] was not found. This file is required before running this task. Please generate it first using [relevant task file]."

Do not proceed with a missing required input.

### 2c. Input File Freshness Check

After confirming each input file exists, check its `date` frontmatter field against today's date. If the file is older than **7 days**, stop and ask the user:

> "[filename] was last generated on [date from frontmatter], which is more than 7 days ago. I recommend regenerating it first so this analysis reflects current conditions. Would you like me to regenerate it, or proceed with the existing file?"

If the user chooses to proceed with a stale file, note the staleness warning in the output file under the `inputs_used` frontmatter field:

```yaml
inputs_used:
  - "macro-outlook.md (date: 2026-05-01) — WARNING: file is 15 days old"
```

**Staleness threshold: 7 days.** This applies to all input outlook files unless the task document specifies a different threshold for a specific file.

---

## 3. Task Document Structure

Every task document must include the following sections in this order:

1. **Frontmatter** — copyright, date, task name, agent file reference, output path
2. **Standard Prompt** — the canonical prompt text, plus the confirmation question for the user
3. **Pre-Flight Checks** — existence and freshness checks for all required input files, plus the output frontmatter standard
4. **Agent Guidelines** — agent identity, framework summary, output format requirements
5. **Data Collection Method** — numbered steps listing tools and sources the agent will use
6. **Output File** — the destination path for the generated output

---

## 4. Task Document vs. Output File

**Task document** (`*-task.md`): A durable, reusable instruction file that defines how to run a task. Stored in `context/trading-agent/`. Not regenerated each run — updated only when conventions or agent instructions change.

**Output file**: The generated analysis produced when the task is run. Stored in `context/trading-agent/output/`. Regenerated on each run. Must carry the full frontmatter standard from Section 1.

---

## 5. Output File Location

Unless a task document specifies otherwise, all generated output files are saved to:

```
context/trading-agent/output/
```

Name output files descriptively and consistently, e.g.:
- `macro-outlook.md`
- `value-stock-list.md`
- `swing-trade-list.md`
- `options-income-list.md`

---

## 6. Applying These Conventions to New Task Documents

When creating a new task document:

1. Read this file (`task-conventions.md`) first.
2. Identify the agent instructions file in `context/trading-agent/`.
3. Identify all required input files (e.g., `macro-outlook.md`) and add them to the Pre-Flight Checks section with the 7-day freshness rule.
4. Include the prompt confirmation step as the first action in the Pre-Flight Checks section.
5. Set the output path to `context/trading-agent/output/<output-filename>.md`.
6. Include the frontmatter template from Section 1 in the Pre-Flight Checks section so the agent knows what to write.

## 7. Data Source Authentication — Finviz

Several agent tasks use Finviz as a primary data source. The public (unauthenticated) version of Finviz returns limited data — key metrics such as full screener columns, insider transactions, earnings data, and extended fundamentals may be missing or truncated. Finviz Elite (paid subscription) unlocks full data access.

### Pre-Flight Step: Ask the User

Before any data collection step that involves Finviz, the agent must ask:

> "Do you have a Finviz Elite login? If so, I can gather significantly more complete fundamental data for this analysis. What is your preferred approach for providing authenticated access?"

Wait for the user's response before proceeding with data collection. If the user has no Finviz subscription, proceed with the public fetch and note any data gaps in the output.

### Authentication Approach Options

Present the user with the following options and let them choose. Do not assume or default — the right approach depends on the user's session state and tooling preference.

| Option                        | Description                                                                                                                                                               | Tradeoff                                                                                                                                         |
| ----------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| Cookie-based fetch            | User copies the `finviz_auth` and session cookies from an active browser session and provides them to the agent. Agent includes them in fetch_webpage requests.           | Lightest approach. Requires user to open Finviz in a browser, inspect cookies, and paste them. Cookies expire; needs refresh periodically.       |
| Exported CSV screener         | User runs the desired Finviz screener with Elite filters applied, exports the CSV, and places it in the workspace for the agent to read.                                  | No automation needed. Requires the user to do the export step manually before running the task. Good for batch runs.                             |
| Playwright browser automation | Agent launches a browser session via Playwright, navigates to Finviz, and authenticates using stored credentials.                                                         | Most automated but heaviest approach — adds latency and complexity. Best for fully unattended runs. Avoid unless the user explicitly prefers it. |
| Manual HTML paste             | User navigates to the Finviz ticker page in an authenticated browser, copies the page HTML or stats table, and pastes it into the conversation. Agent parses it directly. | Simple and reliable for small sets of tickers. Not scalable for lists longer than 5-7 names.                                                     |

### Default Behavior (No Authentication Provided)

If the user does not have Finviz Elite or declines to provide authenticated access, the agent proceeds with public fetch_webpage calls. Any metrics that appear missing or truncated must be flagged in the output with the note:

> "Data collected from unauthenticated Finviz session. Some fields may be incomplete. Finviz Elite authentication recommended for full accuracy."

## 8. Web Request Standards

All HTTP requests made by any agent task — regardless of tool, data source, or method — must use a Chrome user-agent string. This applies to fetch_webpage calls, PowerShell Invoke-WebRequest, curl, Python requests, and any other HTTP mechanism.

### Required User-Agent String

```
Mozilla/5.0 (Windows NT 10.0; Win64; x64) AppleWebKit/537.36 (KHTML, like Gecko) Chrome/124.0.0.0 Safari/537.36
```

### Enforcement by Method

| Method                         | How to Apply                                                                                                                                          |
| ------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| PowerShell `Invoke-WebRequest` | Pass `-Headers @{ "User-Agent" = "Mozilla/5.0 (Windows NT 10.0; Win64; x64) AppleWebKit/537.36 (KHTML, like Gecko) Chrome/124.0.0.0 Safari/537.36" }` |
| PowerShell `Invoke-RestMethod` | Same `-Headers` parameter as above                                                                                                                    |
| curl                           | Add `-A "Mozilla/5.0 (Windows NT 10.0; Win64; x64) AppleWebKit/537.36 (KHTML, like Gecko) Chrome/124.0.0.0 Safari/537.36"`                            |
| Python `requests`              | Pass `headers={"User-Agent": "Mozilla/5.0 (Windows NT 10.0; Win64; x64) AppleWebKit/537.36 (KHTML, like Gecko) Chrome/124.0.0.0 Safari/537.36"}`      |
| fetch_webpage tool             | The tool manages its own headers; if the tool supports a headers parameter, apply the UA string. If not, note this limitation.                        |

Failure to set the correct user-agent is the most common cause of blocked or degraded responses from financial data sites (Finviz, Yahoo Finance, Macrotrends). Do not omit it.
